0The mental model — how AI coding actually works

Before any clicks, understand what you are about to do. You are not learning to code. You are learning to direct a very fast, very literal junior developer who never gets tired, has read most of the internet, but has no idea what your business is until you tell it. Your job is three things only:

1 · Give context

The AI can only make good decisions if it understands your site, your plugins, and your business goal. You feed it that context once, then keep it updated.

2 · Set boundaries

It works on a copy of your site on your own computer (local), never the live site directly. Nothing reaches customers until you press publish.

3 · Review & decide

You judge whether the work is right — especially whether it respects your business logic. You approve; the AI executes. Never the reverse.

The one risk that matters most An AI will happily write code that works but is structurally wrong for your business — because it didn't understand what is foundational versus cosmetic. A wrong button colour is a 2-minute fix. A wrong data model (how your products, members, or orders are stored) can cost weeks. Section 3.5 is the antidote: you debate the AI about what is foundation and what is leaf before it writes anything important.

1Set up your AI cockpit

You install three things, once: (a) a base toolkit (Node.js), (b) an AI coding assistant (the CLI), and (c) two free "skill packs" that make the assistant dramatically better at disciplined work and at WordPress specifically.

1.1 — Choose your AI assistant

Two excellent options. Both run in your Terminal, both can read and edit files and run commands for you. The difference that matters for you: which one the free skill packs are built for.

Recommended
Claude Code

Anthropic's CLI. The two skill packs in this guide (Superpowers + WordPress Agent Skills) are native to it — they install in one command and "just work". Best disciplined-workflow support (it can be told to test before shipping). Best choice for non-developers.

Alternative
Codex CLI

OpenAI's CLI. Very capable and a great fallback if you already pay for ChatGPT. The skills below follow the open "Agent Skills" standard, so they can be adapted to Codex, but it takes a little more manual wiring.

→ This guide is written for Claude Code. Every step works on Codex too; where a command differs, we note it. Pick one and stay with it for your first project.

1.2 — Install the base toolkit & the CLI

You need Node.js (the engine these tools run on) and Git (used to download skills and track changes). Then the CLI itself.

1

Install Node.js (LTS). Go to nodejs.org → click the big LTS download button → run the installer → click Next through to Finish. This also installs npm, the command you'll use next.

2

Install Git. Mac: it installs itself the first time you use it (or get it from git-scm.com). Windows: download from git-scm.com, run installer, accept defaults.

3

Open your Terminal. Mac: press ⌘ Space, type "Terminal", Enter. Windows: open the Start menu, type "PowerShell", Enter.

4

Confirm Node is ready. Type this and press Enter. You should see version numbers, not errors.

node --version   # should print something like v20.x or v22.x
npm --version    # should print a number like 10.x
5

Install the CLI. Paste the line for your choice and press Enter. (On Mac, if it complains about permissions, add sudo in front and enter your password.)

# Recommended:
npm install -g @anthropic-ai/claude-code

# Alternative (Codex):
npm install -g @openai/codex
6

Start it and sign in. Move into a folder for your project first, then launch. The CLI will open a browser to log in the first time.

mkdir my-wordpress-project
cd my-wordpress-project
claude            # (or: codex)  — then follow the sign-in prompt

You're now talking to the AI. Type "hello, what can you do?" to test. Press Ctrl+C twice to exit any time.

"It asked me to approve a command — what do I do?" Good. By default the assistant asks permission before running anything that changes files or your system. Read the one-line summary; if it matches what you asked for, approve it. This is your safety net — keep it on while you're learning.

1.3 — Install the two skill packs

Skills are pre-packaged expertise. Out of the box the AI is smart but undisciplined. These two packs fix that.

Superpowers discipline

From github.com/obra/superpowers. Teaches the AI professional habits: brainstorm before building, test before claiming "done", debug systematically, and stop to get your sign-off at checkpoints. This is what stops the AI from confidently shipping broken work.

WordPress Agent Skills domain

From github.com/WordPress/agent-skills. The official WordPress skill pack: how to build plugins and blocks correctly, follow WordPress coding & security standards, and use WP-CLI (the WordPress command tool). This is what stops the AI from writing un-WordPress-y, insecure code.

Install both (Claude Code). Inside the claude session, skill packs install as "plugins" via a marketplace. Type these as messages/commands to the assistant:

# 1) Add the Superpowers marketplace, then install it:
/plugin marketplace add obra/superpowers
/plugin install superpowers

# 2) Add the WordPress skills the same way (repo: WordPress/agent-skills):
/plugin marketplace add WordPress/agent-skills
/plugin install wordpress-agent-skills
Names can change — verify against the README Repos evolve. If a /plugin install name doesn't match, open the repo's README (the front page on GitHub) and copy the exact install command shown there. As a universal fallback that works for any Agent-Skills repo, you can clone it straight into your skills folder: 
# Universal fallback — works for Claude Code AND Codex:
git clone https://github.com/obra/superpowers ~/.claude/skills/superpowers
git clone https://github.com/WordPress/agent-skills ~/.claude/skills/wordpress
For Codex, place them in Codex's skills/prompts directory instead (see its README) — the skill content is portable; only the folder location differs.

Confirm they loaded. Ask the assistant in plain English:

List the skills you currently have available, and tell me which ones relate to WordPress and which enforce a testing or review workflow.
2Give the AI a memory: context & access

This is the step most people skip — and it's the one that decides whether the AI is brilliant or dangerous. Two files live in your project folder: a context file (what your site is) and a secure access file (how to reach it). Do this carefully.

2.1 — Build the project context

The goal: a single document the AI reads at the start of every session so it understands your plugin/site without re-explaining. The clever part — you don't write it by hand. You point the AI at your plugin/theme code and have it generate the context for you, then you correct it.

Prompt — generate the context file
Read every file in this project (the plugin/theme folder I've placed here). Then create a file called CONTEXT.md that documents, in plain English a non-developer can follow: 1. What this plugin/theme does and the business problem it solves. 2. Its main features and where each lives in the code. 3. Custom data it stores — post types, taxonomies, database tables, options. 4. Integrations — any external services, APIs, or payment/CRM connections. 5. Anything fragile or risky to change. Keep it under two pages. After writing it, list the 5 things you are least sure about so I can clarify them.
1

Put your code where the AI can see it. If you have the plugin/theme files, copy that folder into your project folder. If you don't yet, that's fine — you'll pull them from your live site in Part 3, then run this prompt.

2

Run the prompt above. The AI scans and drafts CONTEXT.md.

3

Correct it — this is the valuable part. Read the draft. Answer its "least sure about" list. Fix anything it misunderstood about your business. The 15 minutes you spend here prevents the structural mistakes warned about in Part 0.

Why this works From now on you can start any session with "Read CONTEXT.md first." The AI inherits a correct mental model instantly, instead of guessing. Keep CONTEXT.md updated as the site grows — treat it as the site's memory.

2.2 — The secure access file (prod.md)

To let the AI work with your real site, it needs connection details: SFTP (file access), the WordPress admin/REST credentials, and sometimes database access. You'll keep these in a file commonly called prod.md (or .env). This file is sensitive — treat it like a password vault.

Security — read before you create this file
  • Never commit it to Git or send it in chat/email. Add it to .gitignore immediately (step 1 below).
  • Use a WordPress Application Password, not your real login. It's a revocable, limited key — if anything leaks, you delete it and the damage stops.
  • Prefer staging credentials over production wherever possible. Give the AI the least access it needs.
  • If your host offers it, store secrets in a manager (1Password, host vault) and reference them — don't paste raw passwords if you can avoid it.
1

Protect it first. Create a .gitignore so the secret file can never be uploaded by accident:

echo "prod.md" >> .gitignore
echo ".env"   >> .gitignore
2

Create the WordPress Application Password. In wp-admin → Users → your profile → scroll to Application Passwords → type a name like "AI Assistant" → Add New Application Password → copy the password shown (you only see it once).

3

Get your SFTP details from your host's control panel (host address, username, password or key, port — usually 22). If unsure, ask your host for "SFTP credentials".

4

Fill in the template. Create prod.md with this shape (replace the bracketed parts):

# prod.md — SENSITIVE. Never commit. Never paste in chat.

## Site
URL:            https://yoursite.com
WP admin:       https://yoursite.com/wp-admin

## WordPress REST API (for content + management)
WP_USER:        your-admin-username
WP_APP_PASSWORD: xxxx xxxx xxxx xxxx xxxx xxxx   # Application Password

## SFTP (for files / plugin deploys)
SFTP_HOST:      sftp.yourhost.com
SFTP_USER:      [user]
SFTP_PORT:      22
SFTP_KEY:       ~/.ssh/id_site   # prefer a key over a password

## Notes for the AI
- This is PRODUCTION. Do not deploy here without my explicit approval.
- Always develop and test on LOCAL first (see Part 3).
How the AI uses this safely You tell the assistant: "Credentials are in prod.md. Use the WordPress REST API with the Application Password to read or create content. Do not touch production files or deploy without asking me first." Because the assistant asks permission before acting (Part 1.2), you stay in control of every connection it makes.
3Local-first development (the safe sandbox)

The golden rule of this entire guide: the AI develops on a private copy of your site running on your own computer (called "local"). You see changes there first. Only when you're happy does anything reach the live site ("production"). This single habit removes ~90% of the risk of AI development.

Local = sandbox

A full copy of WordPress on your laptop. Break it, experiment, undo — customers never see it. No internet visitor can reach it.

Production = live

Your real website that customers visit. Sacred. Changes arrive here only after you approve them locally.

3.1 — Install a local WordPress (one-time)

Recommended
LocalWP (by WP Engine)

Free, visual, one-click. No technical setup. Made exactly for non-developers. Pull your live site into it with a couple of clicks. Use this.

Alternative
wp-env (Docker)

The developer-favourite, fully command-line. More flexible and scriptable, but you'll be installing Docker and reading more docs. Choose only if a developer is helping you.

→ Use LocalWP. It's the fastest path from zero to a working sandbox for a non-developer.
1

Download & install LocalWP from localwp.com → run the installer → open the app.

2

Create a site: click + Create a new site → give it a name → accept the defaults → set an admin username/password you'll remember → Add Site. In ~1 minute you have a working WordPress at a local address.

3

Bring your live site in. Easiest for non-developers: install the free "All-in-One WP Migration" plugin on production, Export the site to a file, then Import that file into your Local site. Now your sandbox mirrors production. (Your host or Blue Coral can do this for you if preferred.)

4

Point the AI at the local files. In LocalWP, right-click your site → Open site shell or Reveal in Finder/Explorer to find the folder. Run claude from inside that folder (specifically the wp-content area where themes/plugins live).

3.2 — Let the AI develop locally

Now the loop you'll repeat for every change. Always brainstorm before building (the Superpowers skill enforces this if you let it).

1 · AskDescribe the change in plain English + the goal behind it.
2 · Agree planAI proposes an approach; you approve or adjust.
3 · BuildAI edits local files; approves each action with you.
4 · TestYou view it in the Local site; AI checks it works.
5 · IterateRefine until right — all still local.
Prompt — a well-formed change request
Read CONTEXT.md first. I want to [describe the change, e.g. "add a 'Download brochure' button on every product page that logs each click"]. The business goal is [why — e.g. "I need to know which products generate brochure interest"]. Before writing any code: tell me your plan, which files you'll touch, and whether any part of this is "foundation" (hard to change later) versus "leaf" (cosmetic). Wait for my approval. We are on LOCAL only — do not touch production.
Always state the goal, not just the task "Add a button" tells the AI what. "So I can track brochure interest per product" tells it why — and the why is what lets it choose a structurally correct solution (e.g. store clicks properly) instead of a quick hack.
3.5The "Foundation vs. Leaf" debate

This is the most important habit in the whole guide, and the cheapest insurance you'll ever buy. Before the AI builds anything non-trivial, you make it separate the foundation from the leaf — and defend the call.

Foundation (the trunk) — get it right, hard to changeLeaf (the branches) — easy to change later
How data is stored: post types, taxonomies, custom tables, fieldsColours, fonts, spacing, button styles
Integrations: payment, CRM, email, external APIsWording and copy on a page
User roles & permissions, membership/access logicWhich widgets show in a sidebar
URL structure & how content is organisedLayout of a single landing page
Anything other features will depend on laterAnything self-contained you can redo in an hour

The danger: the AI doesn't know your business, so it may treat a foundational decision as casual and bolt on a quick fix that traps you later. You break that by forcing a short debate.

Prompt — force the foundation/leaf debate
Before coding, classify this work. Make a two-column list: what is FOUNDATION (expensive to change later, other things will depend on it) and what is LEAF (cosmetic, easily redone). For each FOUNDATION item, propose the option you'd choose and explain the trade-off in plain English — as if I'll have to live with it for two years. Then argue against your own choice once: what would make this decision wrong? Only after we agree on the foundation do you write code.
Push back — you're allowed to disagree with the AI If the AI's reasoning doesn't match how your business actually works, say so: "No — our members can belong to multiple companies, so that one-to-one structure is wrong. Rethink the foundation." The AI is fast and knowledgeable but you are the domain expert. The debate exists so your knowledge shapes the structure before code is written, not after.

3.6 — Review and push to production

Once it's right on Local and you've reviewed it, you promote it to the live site. For non-developers, keep this controlled and reversible.

Recommended
Plugin / managed deploy

Use your host's staging→live "push" button, or a migration plugin, to move tested changes up. Simple, visual, and your host keeps backups. Safest for non-developers.

Alternative
AI-assisted SFTP deploy

Let the AI upload the specific changed files via SFTP using prod.md. Faster for small code changes — but only with a backup taken first and your explicit go-ahead each time.

→ Whichever you pick: back up production first, deploy, then check the live site immediately.
  • Backup taken of production (host snapshot or migration export) before any deploy.
  • Change tested and approved on Local — you saw it work with your own eyes.
  • Foundation/leaf debate done for anything structural.
  • Deploy only the changed files/content, not the whole site, unless doing a full migration.
  • After deploy: open the live site, click through the affected pages, confirm nothing else broke.
  • Know your rollback: "if this breaks, restore the backup from [where]".
Prompt — controlled deploy
The change on Local is approved. Walk me through deploying ONLY the files we changed to production using the SFTP details in prod.md. First: list exactly which files will be uploaded and confirm a backup exists. Wait for my "go". After upload: tell me the precise pages I should check on the live site to verify it worked, and how to roll back if it didn't.
4The prompt-writing playbook

Everything above depends on one skill: writing a clear instruction. A good prompt has six parts. You won't always use all six, but keep them in mind.

PartWhat it doesExample
ContextPoint to what it should know first"Read CONTEXT.md first."
TaskThe concrete thing to do"Add a brochure-download button to product pages."
GoalThe why — enables good judgement"So I can track interest per product."
ConstraintsBoundaries & rules"Local only. WordPress standards. Ask before deploying."
OutputWhat you want back & in what form"Show me the plan as a short bullet list first."
VerifyHow you'll both know it worked"Then tell me exactly how to test it."

Weak prompt

make a button to download the brochure

No context, no goal, no boundaries. The AI guesses — and may guess structurally wrong.

Strong prompt

Read CONTEXT.md first. Add a "Download brochure" button to every product page (task) so I can track which products drive interest (goal). Local only; follow WordPress standards; classify foundation vs leaf before coding (constraints). Give me the plan first (output), then how to test it (verify).

Five habits that make the AI reliable

  • Always give the goal, not just the task — the "why" is what produces correct structure.
  • Ask for the plan before the code — cheap to fix a plan, expensive to undo code.
  • Make it debate foundation vs leaf on anything structural (Part 3.5).
  • Demand a test step — "tell me how to verify this worked" — never trust "done" alone.
  • One change at a time — small, reviewable steps beat one giant request you can't check.
5Golden rules & troubleshooting

The 7 golden rules

  • Local first, always. Develop and test on your computer; production is the last step.
  • Back up before every deploy. A snapshot is your undo button.
  • Secrets never leave prod.md. Use Application Passwords; never commit or paste them.
  • Foundation gets a debate. Structure is expensive to change — decide it deliberately.
  • Content is always "Pending". A human approves every post before the public sees it.
  • You approve; the AI executes. Keep permission prompts on. Read before you approve.
  • One small change at a time. Reviewable steps, tracked in CONTEXT.md / Excel.
SymptomLikely causeWhat to do
AI's code "works" but is wrong for your businessMissing context / no foundation debateUpdate CONTEXT.md; re-run the foundation/leaf debate (3.5) before rebuilding.
Live site broke after a deployUntested change or no backupRestore the pre-deploy backup; reproduce and fix on Local; redeploy.
"Permission denied" / can't connect to WordPressWrong Application Password or SFTP detailsRegenerate the Application Password; re-check host/port in prod.md.
A post went public unexpectedlyA prompt used publishSet it back to draft; fix every prompt to use pending only.
AI says "done" but it isn'tNo verification stepAlways add "tell me how to test this"; confirm with your own eyes.

1How the content engine works

This is a repeatable system that researches, writes, and illustrates blog posts — then drops each one into WordPress as Pending Review so a human approves every word before the public sees it. Nothing auto-publishes. Every stage is logged in an Excel tracker so you can manage and QC the flow at a glance.

Prerequisites from the Develop tab The engine reuses two things you set up in ① Develop the site: the AI assistant (Part 1) and the secure prod.md credentials file with your WordPress Application Password (Part 2). If you skipped those, do them first.

The five stages

1 · CollectGather source articles & references on your topic.
2 · KeywordsExtract the keywords/intents worth targeting.
3 · CreateDraft the content + a matching image per keyword.
4 · PushUpload to WordPress as Pending, one by one.
5 · ReviewYou edit, approve, schedule, publish.

How the data flows (and where humans step in)

Follow one article through the machine. At each stage, something goes in, the AI does work, and a result is written to the Excel tracker. Two checkpoints are human gates — the engine pauses for you.

1
Collect. In: a topic. Out: 3–5 source links + key points → written to Sources column. auto
2
Keywords. In: the sources. Out: one primary + several secondary keywords + intent → written to keyword columns. gate · you approve
3
Create. In: approved keywords. Out: a 600–1,000-word draft + featured image saved to disk; Title / Draft status / Image filled. gate · you approve drafts
4
Push. In: approved drafts. Out: a WordPress post created with status = pending; WP post ID recorded. auto
5
Review. In: pending posts in wp-admin. Out: you publish/schedule; Reviewer / Published date filled. human
The one rule that never changes No matter which setup you choose below, Stage 4 always writes status = pending — never publish. That single setting is your guarantee that AI never speaks to your audience without a human sign-off.
2The Excel tracker (your control panel)

One workbook, one row per article, columns that mirror the five stages. The AI fills columns as it works; you QC each stage by reading the sheet. This is your single source of truth whichever setup you run.

ColumnStageWhat goes here

Topic1The subject of this article

Keep the sheet honest Tell the AI: "After every stage, update the tracker row and never skip a column. If you couldn't complete a step, write why in that cell." Now the sheet shows at a glance what's collected, drafted, pushed, and pending.
3Setup A — Run it through your local AI
Start here
Setup A — Local LLM (assistant-driven)

You drive each stage by prompting your AI assistant in the Terminal; it reads/writes the Excel tracker and pushes drafts via the WordPress REST API. Zero extra tools, full visibility, easy to QC. Perfect for learning the workflow and for low-to-medium volume.

Later
Setup B — n8n (automated)

The same five stages, but running unattended on a schedule. More setup and a monthly cost. Covered in section 4–5. Move here only once Setup A reliably produces posts you'd publish.

→ Prove quality with Setup A first. Automating bad prompts just scales up mistakes.

The run loop

1

Create an empty content-tracker.xlsx with the columns above (or ask the AI to create it). Keep it in your project folder.

2

Open the Terminal in that folder and run claude (or codex).

3

Run the four stage-prompts below in order. After Stage 2 and Stage 3, stop and review in the tracker before continuing — those are your gates.

4

When drafts are pushed, switch to wp-admin for Stage 5 (section 6).

Stage 1 — Collect
For the topic "[your topic]", find 5 strong reference articles. For each, capture the title, link, and 3 key points. Create/append rows in content-tracker.xlsx with the Topic and Sources columns filled. Do not invent sources — only list ones you actually found, and flag any you're unsure about.
Stage 2 — Extract keywords gate
For each row that has Sources but no keywords, extract one Primary keyword, 3–5 Secondary keywords, and label the Search intent — based on the sources, not guesswork. Fill those columns and show me the table so I can approve before Stage 3.
Stage 3 — Create content + image gate
For each approved row, write a WordPress-ready post (600–1,000 words) targeting the Primary keyword naturally, in our brand voice [describe it]. Include a title, meta description, headings, and a relevant featured image saved to /images. Save the post body as a file; update Title / Draft status / Image file in the tracker. Do NOT push to WordPress yet — I review drafts first.
Stage 4 — Push to WordPress as Pending
For each row marked "approved-to-push", use the WordPress REST API with the credentials in prod.md to: (1) upload the featured image to the media library, (2) create the post with status = pending (never "publish"), with title, content and the featured image attached. Record the returned WP post ID and set WP status = Pending in the tracker. Process them one at a time and report each result.
4Setup B — Automate with n8n

n8n is a visual automation tool: you connect "nodes" (little boxes that each do one job) into a flow that runs on a schedule, unattended. It runs the exact same five stages — and still stops at Pending for your review. Graduate here once Setup A's prompts are proven and you want volume without hand-holding.

Easiest
n8n Cloud

Sign up at n8n.io, nothing to install. Monthly fee. Best if you don't run your own server. Recommended for non-technical teams.

Self-host
n8n on Docker

Free software you run on your own machine/server (docker run n8nio/n8n). Cheaper at scale, but you maintain it. Choose with technical help.

→ Start on n8n Cloud; move to self-host only if cost or data-residency demands it.

What the workflow looks like (node by node)

#NodeJob (maps to a stage)
1Schedule TriggerStarts the flow on a timer (e.g. every Monday 07:00)
2RSS / HTTP ReadCollect — pull recent source articles
3LimitTake the few newest items so you don't flood the queue
4HTTP → LLMKeywords — ask the model for primary/secondary keywords
5HTTP → LLMCreate — ask the model for a titled, formatted draft
6HTTP → WordPressPush — create the post with status = pending
7Google Sheets / ExcelLog the row to your tracker for QC
Credentials you'll attach inside n8n (1) Your LLM API key (Anthropic or OpenAI) on the two HTTP→LLM nodes; (2) a WordPress Application Password as an "HTTP Basic Auth" credential on the WordPress node; (3) optionally a Google Sheets connection for the tracker. Store these in n8n's credential vault — never paste them into a node's plain text.
5n8n — sample workflow (import this)

We've prepared a ready-to-import starter workflow with all seven nodes wired together. Import it, then attach your own credentials and adjust the prompts/schedule.

1

Download the file: n8n-content-pipeline.sample.json (next to this guide, in /assets).

2

In n8n, open Workflows → ⋯ menu → Import from File → choose the downloaded JSON.

3

Edit four things: (a) the RSS feed URL on node 2, (b) your LLM API key on nodes 4 & 5, (c) the WordPress Application Password credential + your site URL on node 6, (d) your Google Sheet on node 7.

Excerpt — the WordPress node is hard-wired to Pending on purpose:

{
  "name": "4 · WordPress — create PENDING post",
  "type": "n8n-nodes-base.httpRequest",
  "parameters": {
    "method": "POST",
    "url": "https://YOURSITE.com/wp-json/wp/v2/posts",
    "authentication": "genericCredentialType",
    "genericAuthType": "httpBasicAuth",
    "jsonBody": {
      "status": "pending",   // never change to "publish"
      "title":  "AI draft — review me",
      "content": "={{ $('3 · LLM — draft post').item.json... }}"
    }
  }
}

If a node shows a warning after import, open it and re-select the option — the structure and the prompts are the valuable part. Always run one manual test before scheduling, and confirm the result is Pending, not live.

3
